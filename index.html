Public, source-traceable browser benchmark · React 18.3.1

One cache write. Same final UI. 2 commits become 16.

With eight independently mounted useQuery consumers, Apollo Client 3.6.9 commits one cached result in two steps. Apollo Client 3.14.1 fragments the same work into sixteen. Grouping only the React-facing deliveries restores two.

The low-level mechanism

With multiple consumers, Apollo 3.14.1 can split one cache update across more React commits.

Both versions receive the same data and reach the same final UI. The difference is how many times React must publish intermediate work along the way. Every extra commit can repeat parent rendering, DOM mutation, layout effects, and downstream state work.

R

Render calculates

React calls component functions to calculate the next UI. Many component renders can be combined into one commit.

C

Commit publishes

React applies one completed render result to the DOM and runs commit-phase effects. This is what the benchmark counts.

Why eight in the headline result?

Eight only makes the scaling difference easy to see. It is the largest default case; the suite also tests 1, 2, and 4 consumers.

Why React 18 automatic batching does not merge this

Batching combines compatible updates in one scheduling window. Here, Apollo delivers consumers in separate browser tasks, and each 3.14.1 external-store callback can flush before the next task starts.

What is observed versus source-derived

The experiment directly manipulates delivery-task grouping. The DefaultLane versus SyncLane attribution comes from the pinned Apollo and React source paths; lanes are not independently manipulated by a benchmark arm.

Benchmark rationale and fixture

Remove network noise. Keep the real React pressure.

A product trace can show extra commits, but network timing and application code make the cause hard to isolate. This fixture keeps the relevant application shape—several components independently observing one query—while replacing the network response with one controlled in-memory cache write.

Required application shape

The effect requires multiple independently mounted useQuery calls. Apollo may deduplicate their network request, but the React subscribers remain distinct. Reading the query once and distributing data through props or context creates one query delivery, not N.

function QuerySubscriber({ publishDerivedState }) {
  const { data } = useQuery(SHARED_ITEM, {
    fetchPolicy: "cache-only"
  });
  const value = data?.benchmarkItem?.value;

  useLayoutEffect(() => {
    mount.getBoundingClientRect();
    publishDerivedState();
  }, [value]);

  return <ResultRows count={40} value={value} />;
}

The baseline cache is seeded before measurement. The clock starts immediately before one changed cache.writeQuery and ends after every query value and derived parent update has committed, followed by two animation frames.

The parent update represents ordinary downstream work such as measuring children, registering rows, or updating a shared summary after data renders.

Why the fixture is intentionally non-memoized

Parent updates re-render their consumer subtree, and the fixture recreates each consumer's callback prop. This makes fragmented commits carry visible downstream work and amplifies the 72-render and React-CPU secondary metrics at eight subscribers. Memoized consumers with stable props and callbacks would reduce those secondary totals, but not the primary two-versus-sixteen commit fragmentation.

Measurement boundary

Count commits first. Use timing as supporting evidence.

The primary proof is the exact commit and intermediate-snapshot sequence. Milliseconds vary by browser and machine; the benchmark reports them to show completion cost, not as a universal Apollo timing claim.

Included

Cache publication, Apollo observer delivery, React calculating the next UI, DOM mutation, layout effects, geometry reads, derived parent updates, final commit, and two animation frames.

Excluded

Network time, server time, and application-specific business logic. There is no synthetic busy loop or artificial “commit tax.”

Causal design

Three arms ask one falsifiable question.

Are separately scheduled React-facing deliveries necessary for the extra commits? Comparing the two unchanged packages establishes the version difference. Comparing unchanged and diagnostic 3.14.1 isolates delivery grouping.

Control A

Apollo 3.6.9 stock

The exact published 3.6.9 package, unchanged. It establishes the older version's commit pattern for the same tree and values.

Treatment B

Apollo 3.14.1 stock

The exact published 3.14.1 package, unchanged. It establishes whether the version difference appears without any patch.

Causal probe C

3.14.1 + diagnostic batching

The same 3.14.1 React path and values, but pending observer callbacks drain in one shared task. Only delivery grouping changes.

Prediction: if separated deliveries cause fragmentation, one subscriber should be a negative control where every arm has two commits. As subscribers increase, stock 3.14.1 should grow to 2N commits while stock 3.6.9 and grouped-delivery 3.14.1 remain at two.

This patch is evidence, not a release recommendation.

It relies on Apollo private objects and adds a task of queueing delay. A durable fix should preserve the ordering guarantee introduced by Apollo PR #11083 while coordinating publication through a supported library boundary.

    Pinned source evidence

    The code paths explain the measured task timeline.

    Both versions schedule one separate zero-delay notification task per watched ObservableQuery. The public sources show that a delivered result then asks React for a different kind of update.

    Apollo 3.6.9

    Ordinary local state update

    observer result
  → setTick(tick => tick + 1)
  → requestUpdateLane(...)
    1. Outside a browser event, React assigns ordinary DefaultLane priority.
    2. Compatible pending work can coalesce before React commits.
    →
    Apollo 3.14.1

    External-store consistency update

    observer result
  → handleStoreChange()
  → forceStoreRerender(..., SyncLane)

    “External store” means state owned outside React—in this case, Apollo's query store.

    1. React's forceStoreRerender assigns synchronous SyncLane priority.
    2. A React microtask can commit before Apollo's next separate delivery task.
    Evidence boundary

    The live timeline verifies separate host tasks, observer callbacks, microtasks, and commits. The lane names above are the source-traced explanation for those pinned versions, not a fourth benchmark variable. PR #11083 introduced the external-store callback to fix update ordering, so simply restoring the old setter is not a safe fix proposal.

    Interpretation

    What the benchmark does—and does not—establish

    Established by the proof

    • The exact version-specific commit pattern is reproducible with public packages and a small React tree.
    • Every arm receives the same number and order of logical values and reaches identical final UI state.
    • Grouping only the React-facing deliveries removes the extra commit fragmentation in this scenario.
    • The observed task and microtask sequence matches the linked Apollo and React source paths.

    Not established by the proof

    • That every application upgrading to Apollo 3.14.1 will become slower.
    • That querying once and sharing data through props or context has the same fan-out as N independent useQuery calls.
    • That the fixture's 72 renders or React-CPU multiplier survives consumer memoization with stable props unchanged; those are deliberately amplified secondary metrics.
    • That browser timing deltas will have the same size on another screen or machine.
    • That all query shapes, fetch policies, or React versions follow this exact path.
    • That lanes were independently varied; their attribution is derived from the pinned public source.
    • That the diagnostic patch is a supported or production-ready fix.

    Reference glossary

    Terms used in this lab

    Short definitions for the Apollo, browser-scheduling, React, and statistics language visible above.

    Stock
    An exact published package used without modifications. The benchmark loads Apollo Client 3.6.9 and 3.14.1 directly from esm.sh.
    Diagnostic patch / diagnostic batching
    A deliberately narrow experimental change used to test a causal hypothesis. Passing the test supports the mechanism; it does not by itself make the patch safe for production.
    Subscriber
    A mounted consumer registered to receive query-result changes. In this benchmark, each subscriber is one React component calling useQuery.
    Apollo cache write
    A synchronous call that places a GraphQL-shaped result into Apollo's in-memory cache and starts publication to interested queries. The benchmark uses cache.writeQuery.
    ObservableQuery
    Apollo's live query object. It tracks a query result and sends changes to registered observers, including the subscription behind useQuery.
    Observer delivery / observer.next
    The callback boundary where one ObservableQuery hands a result to one registered observer.
    Notification
    A signal from Apollo that a watched query may have a new result. This lab distinguishes the signal from the later observer callback that reaches React.
    Host task
    One browser event-loop turn created by work such as setTimeout(..., 0). The browser may run microtasks before starting the next host task.
    Microtask
    High-priority queued work that runs after the current JavaScript stack and before the browser starts the next host task. Promises and React's synchronous flush scheduling can use microtasks.
    React commit
    The phase where React applies one completed render result to the DOM and runs commit-phase effects. Several component renders may belong to one commit.
    Component render
    One call of a React function component while React calculates the next UI. Rendering computes changes; committing applies them.
    Derived state
    React state calculated from another result. Here, each subscriber reads its committed DOM geometry and increments a parent summary.
    Layout effect
    A useLayoutEffect callback that runs after React changes the DOM but before the browser paints. The benchmark uses it to read geometry and publish derived state.
    React CPU
    The sum of React.Profiler actualDuration values for measured commits. It covers React render work, not all JavaScript, layout, or browser paint cost.
    Geometry read
    A synchronous DOM measurement such as getBoundingClientRect. It can require the browser to bring layout information up to date.
    Final commit
    The first commit after which all subscribers display the new result and the parent has processed every derived update.
    Paint / final paint
    Paint is when the browser turns committed DOM and styles into pixels. This lab's final-paint boundary is two animation frames after the final commit; it does not use browser paint-timing internals.
    p50
    The median: after sorting the measured values, half are at or below it and half are at or above it. The benchmark also reports p90 in the advanced table.
    p90
    The value at or below which 90% of measured samples fall. It gives more visibility into slower samples than the median does.
    Balanced block
    A mirrored run sequence—ABCCBA or CBAABC—that gives each experiment arm comparable early, middle, and late positions.
    Proof condition
    An invariant that must pass for the run to be accepted, including version checks, final-value equality, exact delivery counts, task order, and commit progression.
    Snapshot
    A compact record of what each subscriber displayed at a commit. For eight subscribers, 11110000 means four new values followed by four old values.
    Logical notification
    One result publication to one observer. All three arms must preserve exactly one logical notification per subscriber.
    Delivery batch
    Observer callbacks drained together by the diagnostic scheduler. The patched arm must deliver every queued value, in order, in one batch.
    DefaultLane
    React's ordinary priority lane for updates in this tested outside-event context. Compatible work can remain pending and coalesce before a commit.
    SyncLane
    React's synchronous priority lane. React 18.3.1's external-store consistency update explicitly uses it and schedules a prompt flush.

    Public, product-independent reproduction. Exact benchmark source, diagnostic intervention, and reference JSON are available in the repository.
